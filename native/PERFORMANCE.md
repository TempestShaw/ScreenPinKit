Host: Apple Silicon, macOS 15.6.1, AppleClang 17, release build, Homebrew Qt 6.11.2. This is initial core-migration evidence, not feature parity or a release qualification.

## Latest: preferences, configurable hotkeys and one-image recovery

The control panel now has Workspace and Preferences pages, primary capture/paste cards, last-image preview and clear/disable controls. Capture/paste/restore global bindings persist in QSettings. Native registration conflicts keep the old bindings; recording a shortcut temporarily releases the app's global registrations so an existing chord can be recorded without triggering capture/paste.

At most the current write and newest pending image exist during encoding; no full image is retained by the history manager after completion. A small clean thumbnail is encoded in PNG metadata so the panel does not decode the original image. The regression suite also covers repeated restoration: inheriting old thumbnail metadata caused recursive file growth, reproduced before fixing thumbnail generation. Clear waits for an in-flight write before removal, preventing resurrection on clear/quit.

Mac: 19 functional QtTest methods pass, including real native registration conflict/rollback and suspension, persistent bindings, restored pixels/DPR/position/zoom, bounded repeated restores, latest-write ordering and clearing during writes. Earlier inline-text/Element regressions remain in the suite.

Windows: actual MSVC 2022 / Qt 6.8.3 x64 build. 18 functional methods pass, including the separate OCR subprocess explaining its missing MSIX identity. The deployed OCR worker loads with Qt removed from PATH, checking app-local Qt/MSVC DLL deployment. This does not establish packaged OCR success, GUI behavior or clean-machine installation.

## Previous: inline text entry and stable Element previews

Text entry now uses a child plain-text editor directly inside the selection or pin. Enter finishes the annotation, Shift+Enter adds a line, and Escape cancels only the draft. The editor grows with its content, stays within the image/selection, and has no visible scrollbars. Chinese text, multiline painting, history and original-resolution export are covered by tests.

The Element flicker was reproduced twice with a fixed 160 × 90 result: moving one pixel inside that element changed the preview to its 800 × 500 window. The old code only reused a result at the exact queried pixel. The corrected code retains a containing element while an asynchronous query is pending, still accepts fresh child targets, and rejects results from other windows or an earlier mode generation. Transient unavailable results do not erase a still-valid preview. No recurring idle timer was added.

All 15 functional QtTest methods pass (17 results including setup/cleanup; CTest 1.23 seconds). New regressions cover continuous movement within an element, delayed results, mode/window changes, child targets, inline entry/cancel/history, Chinese field sizing, zoom and Retina output.

Cua Driver verified the signed packaged macOS app: inline Chinese entry on a pin and capture selection, multiline entry, draft cancellation leaving the pin open, Enter leaving the selection active, and pin export retaining the committed text. Evidence includes `inline-text-preview.png`, `inline-text-multiline.png`, `inline-text-canceled.png`, `inline-capture-preview.png` and `inline-capture-exported.png` in the ignored build directory. Input required the authorized desktop fallback where window-targeted delivery did not reach the active editor reliably.

Tab reached Element mode without a new permission prompt. The driver's full-screen overlay remained the frozen target and exposed no accessible element, so this run only verifies that fallback and mode switching; it does not establish stability of native AX hit-testing in other apps. The deterministic regressions establish the corrected preview/result logic. Windows runtime and achieved display FPS remain unverified.

## Resident process

One locally launched native process with its control panel and a 600 × 321 image pin was sampled five times at 10-second intervals. `ps` reported 0.0% CPU at each sample, RSS 82,064–82,128 KiB (approximately 80.2 MiB), and cumulative CPU time rose from 0.24 to 0.25 seconds across 40 seconds. Sampling is coarse and does not prove zero CPU or zero wakeups. No activity/capture occurred during this interval. Raw samples are in the ignored build directory, `idle-samples.json`.

After real pin interaction, annotation and native save dialogs, the packaged process was sampled again with one 640 × 400 annotated pin and the control panel present. Five samples over 40 seconds reported 0.0% CPU, RSS 101,616–103,936 KiB (approximately 99.2–101.5 MiB), and unchanged cumulative CPU time of 1.41 seconds at `ps` resolution. Screen Recording authentication was still pending and no capture occurred. Raw samples are `post-interaction-idle-samples.json` in the ignored build directory; this is idle observation, not a zero-wakeup guarantee or capture-memory measurement.

Follow-up measurement after the user granted permission used `vmmap -summary` as well as `ps`. A freshly restarted packaged process with the control panel and no pins reported RSS 109,536 KiB (107.0 MiB) and **physical footprint 32.3 MiB**. A preceding restart reported footprint 33.2 MiB. RSS and footprint are different metrics; the earlier 99–102 MiB RSS observation must not be described as private app memory. Apple's [memory diagnosis overview](https://developer.apple.com/videos/play/wwdc2021/10180/) distinguishes dirty/compressed footprint from clean file-backed memory. Hiding the panel after a failed permission attempt reported footprint 35.7 MiB, so merely hiding it did not demonstrate a footprint reduction. Samples are `memory-baseline.txt`, `memory-restarted-baseline.txt`, and `memory-hidden-controls.txt` in the ignored build directory.

At the current display modes, one 32-bit image per display requires 3840 × 2400 × 4 + 5120 × 2880 × 4 = 95,846,400 bytes (91.4 MiB), before window/compositor buffers. This is a pixel-storage calculation, not an observed capture peak. The implementation keeps full frames only during selection and crops the accepted region; real capture peak and recovery remain unmeasured while the signing/permission issue below is unresolved. Further memory work should first measure these buffers and their lifetimes. A shared C++ core with AppKit/Win32 rendering is a possible larger migration, but no lower-memory native-shell prototype has been measured.

## Installed Snipaste comparison

The installed macOS Snipaste is 2.8.6, Universal (arm64/x86_64), with 93,172,597 bytes (88.9 MiB) of regular bundle files. Its bundled QtCore identifies as Qt 6.2; the [official v2.8 changelog](https://www.snipaste.com/download.html) specifies Qt 6.2.4. This local Mac bundle is not a few-megabyte installation.

Cua's initial app inventory omitted a running translocated Snipaste instance. The subsequent launch resolved that existing process, which started on 2026-09-23; this was not a clean launch. Its first `ps` samples reported RSS 29–30 MiB, while `vmmap` reported footprint 229.0 MiB, peak footprint 442.7 MiB, and 217.0 MiB in its swapped column, including 157.7 MiB of IOSurface regions. Later samples changed to RSS 216.0 MiB and then 143.3 MiB, with a later footprint of 192.2 MiB and 115.4 MiB of IOSurface virtual regions. These samples demonstrate that a low resident-page reading alone does not describe the app's full memory charge. Neither the peak nor the intervening activity was a controlled capture measurement.

Four paired idle samples over 30 seconds reported 0.0% CPU for both applications and unchanged cumulative CPU time at `ps` resolution. The native process reported RSS 83.2–83.4 MiB during that interval, with a later footprint of 41.6 MiB. Snipaste has retained state from 18 days of use; the native process has no pins and a different feature set. These are current-state observations, not a matched-workload ranking. The original Snipaste process was not quit, its settings/history were not edited, and its existing pins were not removed.

The historical [v1.16 changelog](https://www.snipaste.com/download.html) documents `Misc/squeeze_memory` and explicitly notes the possible cost to entering-snipping response time. This option is absent from the current [advanced-config documentation](https://github.com/Snipaste/feedback/wiki/Advanced-Configs), so it has not been assumed to work on this installed Mac version or enabled. Current official documentation describes GPU acceleration for mosaic, Gaussian blur and shadows; it does not establish the renderer or frame rate of the selection box. Private implementation details cannot be established from the public feedback repository.

Useful follow-up work is to measure full-frame/window-surface lifetimes, avoid repeated composites when no annotation changes, and gate any memory-saving cache eviction on capture/first-frame latency. Existing immutable frames, region-limited repainting and annotation objects already implement part of this approach; lower footprint after real multi-display capture still needs measurement. Raw observations are `memory-snipaste-idle.txt`, `memory-snipaste-later-idle.txt`, `memory-native-comparison-idle.txt`, `memory-native-later-idle.txt`, and `snipaste-comparison-idle-samples.json` in the ignored build directory.
